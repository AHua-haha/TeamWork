# Workspace usage contract

Workspace provides project registration, model choices, initialization review, filesystem design discovery and project file access. Team owns member configuration/chat; Agent owns execution/context/history. Workspace persists registration/models in its own data model. Project context documents remain filesystem-authoritative; its context index is disposable memory.

## Registration and model choices

`new WorkspaceService(store, config)` takes a WorkspaceStore and configuration capability `issuesFor(settings)`. `list()`, `get(id)`/`record(id)` return registered workspace records with id, name, canonical directory and creation time. Missing records return `not_found`/404; calls after service closure return `workspace_unavailable`/503.

`inspectInitialization({directory, adopt})` is read-only. Directory is an absolute path of at most 1024 characters; adopt selects an existing real folder rather than creating a new or empty one. Overlap with any registered directory is refused, including ancestor/descendant overlap with case-insensitive comparison. The result is `{directory, cleanupPaths, cleanupRevision}`. Nonempty managed metadata outside the chosen project context requires explicit reviewed cleanup consent; null revision means no nonempty cleanup was found.

`create({workspaceId?, name, directory, adopt, models, cleanupRevision?})` validates the name (1–200 characters without control characters), optional id, models and cleanup digest. It serializes creation, rechecks directory/registration state, stages approved non-context `.rsi` metadata and prepares only missing root DESIGN and Lead bundle files. Core coordinates registration, models, Lead and initial activation atomically in SQL. Existing context bytes, project source and Git are preserved. Preparation failure attempts to restore staged metadata/remove this attempt's additions. Cleanup after a successful commit can itself fail; do not infer that every creation failure means registration rolled back. No context README is generated by initialization.

`models(id)` returns `{revision,value:{models,defaultModel},issues}`. `updateModels(id, revision, value)` validates 1–50 choices and a default included among them, checks provider availability and persists against the current revision. Missing prior settings start at revision 0. Stale revisions conflict; legacy empty settings return issues until configured. `defaultSettings(id)` derives the default run settings; it refuses when no default exists. Model configuration and member-file activation are separate workflows.

For HTTP consumers, use `POST /workspaces/initialization`, review its response, then submit `POST /workspaces` with the same intended request and any required cleanup revision. Canceling the review performs no write. `GET/PUT /workspaces/:id/models` exposes model choices. See [API](../../../api/_ctx/README.md).

## Context roots and bindings

`workspaceContext(directory)` locates the one real `.rsi/<project-name>/` root, preserving an existing root after a checkout rename. Multiple roots, symbolic roots, reserved/conflicting names and the retired `.rsi/context/` layout are explicit errors; no implicit migration or deletion occurs. Fresh roots use the checkout directory name independently of its display name.

A directory design owns its mirrored `_ctx/DESIGN.md`; a file design owns `<full-file-name>.ctx/DESIGN.md`. Ordinary directories preserve paths and do not create designs. Only real source nodes with their own valid DESIGN bind to a design system. Other source nodes remain unbound and their context belongs to the nearest owning design part. Missing DESIGN, wrong-type/missing source nodes, links and invalid metadata appear as diagnostics where supported. Internal context files and README inclusions do not create child designs.

Historical assignment identifiers can resolve through the existing project `_ctx/internal/context-migration.json` references map. This is not support for old context folders. `DesignService` lists/inspects/reads current designs, checks assignments, returns working source paths and expands working roots to all descendant designs. Design content is read on demand and SHA-256 revised; the list's revision identifies its index snapshot. It does not edit DESIGN or manufacture user decisions.

## Explicit metadata refresh and loading

`await service.contextManager(id)` returns one resident `ContextBaseManager` for the registered canonical directory. It is initially unrefreshed. `snapshot()` returns null or the last published immutable metadata model. `refresh()` serializes scans and publishes a new epoch/generation revision only on success; failures do not replace the last model. There is no watcher or automatic per-model-call synchronization.

```ts
const manager = await workspaces.contextManager(workspaceId);
const snapshot = await manager.refresh();
const root = manager.design('.', snapshot);
const design = await manager.loadDesign('.', snapshot);
const readmeOnly = await manager.loadUsageReadme('.', snapshot);
const consumer = await manager.loadConsumerContext('.', snapshot);
// consumer: {revision, projectPath, readme: {path, content}, files: [{path, content}]}
```

The last call requires a usage README. Metadata refresh reads headers but retains no document bodies or included file contents. `loadDesign()` reads DESIGN; `loadUsageReadme()` returns README alone or undefined without following includes. File Harness dependency refresh uses the README-only method. Explicit `loadConsumerContext()` reads README plus included files/directories recursively and deduplicates paths. No shell commands or external retrieval are executed by metadata.

A README's YAML front matter is delimited by standalone `---` lines. `summary` is an optional nonempty string; `include` is a list of project-root-relative file/directory paths. Empty lists are allowed. Traversal outside the root, backslashes, control characters, colon paths and symlinks are rejected. Includes supplement the usage contract and are not automatically expanded whenever a README is shown.

Defaults are 50,000 source entries, 10,000 context entries, 64 KiB metadata, 1 MiB per text file, 4 MiB total consumer context and 200 included files. Constructor options override positive safe-integer limits. Source scans omit `.git`, `.rsi`, common dependency/build/environment/cache directories, `.run`, `.claude` and `.playwright-cli`. A direct include can name context documents under `.rsi`; recursive directory expansion still applies exclusions.

A scan is not an atomic filesystem snapshot. Loading verifies README header identity against the selected metadata index, and individual text reads check size/time/inode consistency and UTF-8. Changed/disappeared documents can raise `context_changed`/409; refresh and retry. Missing includes fail explicitly; absent README gives `consumer_context_unavailable`/404; invalid metadata and size/traversal limits fail without returning a partial consumer result. `close()` drains queued scans and invalidates further access. `WorkspaceService.close()` drains creation and closes resident managers.

## Ordinary project files

`await service.files(id)` returns `ProjectFiles` for the workspace directory. `tree(path,depth)` accepts depth 1–16, returns sorted entries and a truncation flag (2,000-entry cap). `find(q)` searches file paths case-insensitively breadth-first (1–200-character query, 200-result/50,000-examined caps). `read(path)` returns UTF-8 text, byte-based revision, size and modification time. `save(path,content,baseRevision)` uses a previous revision to replace or null to create, creates parents and atomically renames a temporary file while preserving existing permissions. Conflicting/missing revisions fail; a matching unchanged write is a no-op. This is optimistic checking, not a filesystem compare-and-swap against arbitrary concurrent external writers.

Paths are relative, cannot traverse links, and exclude top-level `.git`/`.rsi`; special/binary/oversize files fail explicitly. The separate context manager reads context metadata. These file/design services are internal capabilities; current workspace HTTP routing exposes registration/metadata/models, not general file editing, Git baselines or SQL file-history endpoints.

This review leaves DESIGN intent unchanged, adds no internal-context format and does not run initialization, reset or migration. Include references supplement this contract and must be opened when source detail is needed.
