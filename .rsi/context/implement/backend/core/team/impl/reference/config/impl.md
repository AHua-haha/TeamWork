# Config system implementation

## Contract

[Config design](design.md). Editable records can change at any time; resolution returns a consistent copy that an agent run keeps until completion.

## Responsibilities and decomposition

- A TypeScript config service validates app settings, provider connections, catalog entries, and per-agent settings; exposes CRUD, model choices, and run resolution. It also validates and resolves the run settings of team members, which are the same fields, and reports what stops a set of settings from running.
- A small secrets module encrypts provider API keys before persistence and decrypts them only for discovery and run snapshots.
- The database system stores versioned JSON records, atomic edits, and consistent resolution reads in MySQL.
- The runtime resolves one config snapshot before accepting input and passes it to policy hooks for each step.
- The HTTP layer exposes config operations and preserves backend validation and revision conflicts.

## Coordination and data flow

The backend loads deployment config and builds its provider registry before constructing ConfigService and runtime. `createBackendModels` composes Pi built-ins with backend-owned provider catalogs, including Modelflare. Startup then initializes MySQL and the editable app record before accepting requests. The config service validates edits against this registry. A connection stores an endpoint, request protocol, and encrypted optional API key; read APIs return a redacted connection. Known Pi models are listed for that provider with the connection's effective protocol. `reasoningScale` (`off, low, medium, high, xhigh`) is the only accepted entry reasoning value. `reasoningChoices` returns the whole scale for reasoning models with `defaultReasoning: 'off'` and `reasoningSentAs`, which maps each scale level through Pi's `clampThinkingLevel` for that model; non-reasoning models return no levels, `null`, and an empty map. Model choices and capabilities return these fields to the frontend and run validation. An explicit refresh POST requests `/models` with Bearer auth for OpenAI-compatible endpoints, or `/v1/models` with Anthropic version and API-key headers for Anthropic-compatible endpoints. Anthropic pagination is followed before the result is persisted. Discovered choices are cached under the connection identity. A change to provider, URL, or protocol deletes that cache atomically with the connection edit.

`RunSettings` is the part of an agent's settings that a run needs: connection and model, tool and prompt options, instructions, and `modelOptions`. `validateRunSettings` checks it, and an agent's settings are a name plus run settings. `issues` judges run settings, so the agent list, the config read, `issuesFor` for team members, and run resolution share one rule. `resolveForRun` reads an agent's record from the bundle and `resolveSettings` takes run settings and a revision from the caller; both end in one `resolve`, so a run cannot tell an agent from a team member. `configBundle` is read without an agent for members.

Starting a run reads a consistent set of records and resolves the selected connection, model, tools, prompt, and the `modelOptions` entry matching the selected connection and model. Missing reasoning uses the model default; the level is translated through `reasoningSentAs`, and a translated `off` omits Pi's reasoning option. Validation issues consider only that selected entry, so saved entries for other models never block a run. It builds a run-local Pi provider collection with the selected endpoint, protocol, and key. A Pi-known model keeps its identity and capability metadata; when the connection protocol differs from its catalog default, the selected adapter is registered for this run. Built-in Pi models drop their original protocol compatibility overrides; backend-owned providers assemble their own compatibility settings for the selected protocol. The runtime holds that result until the run ends. A later edit is visible only to a later resolution.

The Modelflare catalog explicitly maps exact model IDs to selected upstream provider definitions; only model capabilities are reused, while gateway endpoint, authentication, protocol compatibility and unpriced cost metadata belong to the Modelflare registration. Missing model definitions come from official documentation. The provider inventory records the observed complete model list and provenance. Known unsupported entries and unsupported model/protocol pairs are filtered from cached and refreshed Modelflare choices. `bindModelflareModel` assembles gateway-owned compatibility settings for the selected connection protocol, preserving the shared capability definition. No upstream API-key environment or OAuth fallback is used. Pi rates are unpriced (zero), rather than copied from a different provider. Registration performs no network request and does not mutate existing connections.

## Decisions and constraints

The initial app record contains `title`, `maxInputBytes`, and `allowAgentCreation`. Provider connections are a separate config scope; their encrypted keys use AES-256-GCM and `CONFIG_ENCRYPTION_KEY` from deployment config. Catalog entries are registered-tool choices or prompt templates; provider connections and saved discovery results provide model choices. Unknown discovered models receive conservative Pi metadata. Agent records contain `name`, connection/model selection, selected tool/prompt IDs, direct instructions, and `modelOptions`: per-model entries `{connectionId, modelId, reasoning?, temperature?, maxTokens?, contextBudget?}` with at most one entry per model. Entry validation checks field types and ranges independent of the model; fit to model metadata is reported as an issue for the selected entry. Reading an agent record drops the legacy `callOptions` field, a stored `workspaceId`, and any entry reasoning outside the scale; writes that include `callOptions` or `workspaceId` are rejected as an unknown field, and an out-of-scale reasoning value is rejected as invalid. An agent has no workspace, and the run snapshot carries none. Clamping is computed when choices are built, so a Pi upgrade changes sent levels without rewriting saved entries. `temperature` and `maxTokens` are passed to Pi when present, and reasoning as described above. `contextBudget` is retained on the run snapshot for the runtime policy and does not trigger automatic compaction. There are no long-lived config locks or automatic model fallbacks. Initialization migrates earlier model entries into individual connections and moves agent selections to provider/model fields, including discovered custom models. Legacy model records are hidden from the new catalog API.

## Verification

The [provider unit tests](../../../../../../../../../backend/test/providers.test.ts) verify complete inventory accounting, exact upstream capability reuse, documented additions, gateway credential isolation, protocol filtering, immutable binding, and real Pi streaming request serialization through injected mock transports. The MySQL integration tests verify offline choices, stale-cache precedence, capability visibility, protocol changes, settings validation, and independent run snapshots.

TypeScript check, real-MySQL CRUD/revision/snapshot integration, credential redaction and rotation, legacy migration, runtime mid-run edit behavior, endpoint discovery and Pi calls to mocked custom and cross-protocol known-model endpoints, HTTP API tests, and build. [Integration tests](../../../../../../../../../backend/test/integration/backend.test.ts) also check that Pi-known DeepSeek and OpenAI models report the shared scale with Pi's clamped sent levels, that non-reasoning models report none, that `minimal`/`max` writes are rejected and stored out-of-scale levels read as unset, and that per-model settings are kept across model switches, validated only for the selected model, isolated between agents, and stripped of legacy `callOptions`, against disposable MySQL 8.4. They also check that an agent config with `workspaceId` is refused on create, update, and over HTTP, and that one stored with it reads without it. The [team tests](../../../../../../../../../backend/test/team.test.ts) check that members' settings are judged by the same issues.

The team adds harness-readiness checks around settings resolution and supplies member tools independently; nonempty member catalog tool selections are reported as an issue. ConfigService remains the sole validator/resolver of shared model and prompt settings.
