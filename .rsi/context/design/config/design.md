# Config system

## Purpose, responsibilities and boundaries

Config has four scopes. Deployment-owned **system config** starts the backend and database and supplies the encryption key; it has no CRUD API. Editable **app config** holds product-wide settings. Editable **global agent config** holds provider connections and the tool and prompt options available to agents; it supplies choices, not defaults. Editable **agent config** belongs to an agent that works outside any workspace: it selects one connection and model, tools and prompts, and owns the agent's instructions and model-call settings. Those fields, called **run settings**, also configure each member of a workspace's [team](../workspace-agent/team/design.md); the team stores a member's settings with the member, and this system validates and resolves them by the same rules. The runtime owns the loop, context, requests, and tool execution. The database owns persistence.

## Interface contract

- The backend receives its database URL and encryption key at startup. An editor supplies full editable values and the last read revision for an update or delete.
- App config contains title, maximum input bytes (1 KiB–2 MiB), and whether new agents may be created.
- A provider connection contains a label, provider identifier, base URL, request protocol, and an optional write-only API key. The supported protocols are OpenAI Chat Completions, OpenAI Responses, and Anthropic Messages. The selected protocol governs calls for every model on that connection, including a Pi-known model. Registered providers and their model definitions remain backend-owned and supply model identity and capabilities. A compatible endpoint may supply additional model IDs through discovery. Users do not type model IDs.
- Tool options identify registered backend handlers; prompt options contain reusable text. Neither a provider connection nor a tool option creates an executable handler.
- **Run settings** are `connectionId`, `modelId`, selected tool option IDs, selected prompt option IDs, direct instructions (`prompt`), and `modelOptions`: the model-call settings for each model that has been configured. An entry is `{connectionId, modelId, reasoning?, temperature?, maxTokens?, contextBudget?}`; at most one entry exists per `(connectionId, modelId)`. Model-call settings belong to one agent or member and one model: they are not shared with another, and switching the selected model never copies, rewrites, or removes another model's entry. A model with no entry, or an omitted field, uses its default. New run settings may have no model until configured. An agent config is a `name` plus run settings; a team member's name belongs to its team.
- An agent has no workspace. A team member works in its team's workspace, which the team records; run settings never name one.
- `reasoning` is one of the shared reasoning scale `off`, `low`, `medium`, `high`, `xhigh`; other values, including Pi's `minimal` and `max`, are rejected. `temperature` is 0–2. `maxTokens` is a positive integer. `contextBudget` is a positive token threshold. It is saved in the run snapshot for the runtime's context policy; this version does not automatically compact history when the threshold is reached.


- The backend offers CRUD for editable app, connection, tool, prompt, and agent records. Records have revisions; stale writes fail with conflict. Editing is allowed while an agent runs or references the record.
- A connection's model list combines registered models for its provider with models discovered from its endpoint. The backend returns model IDs, capabilities, and the connection's effective protocol. Every reasoning-capable model offers the full shared scale `off, low, medium, high, xhigh`; a model without reasoning support offers no levels. Each choice also states, for every scale level, the thinking level actually sent: the level itself when Pi declares it supported for that model, otherwise Pi's nearest supported level (the next higher one, else the next lower one). For example, a model supporting only `off, high, max` sends `low` and `medium` as `high` and `xhigh` as `max`; a model that cannot disable thinking sends `off` as its lowest level. Each choice states its **effective default**: `off` for reasoning models and none otherwise. Registered models are available without a network call. Modelflare is a predefined provider (`modelflare`), registered by the backend at startup. Its supported agent models have explicit capability definitions sourced from installed Pi definitions or official model documentation; no frontend model registration or endpoint refresh is required. Its choices are limited to the documented APIs supported by each model; use separate connections when models need different protocols. Listing metadata does not guarantee account access. The source inventory identifies media and specialized models that the agent chat runtime does not support; these known unsupported IDs are excluded from Modelflare agent choices, including after discovery. Explicit refresh queries `/models` for OpenAI-compatible endpoints or `/v1/models` for Anthropic-compatible endpoints, using each protocol's authentication and required version header. Anthropic pagination is followed so the saved list is complete. Refresh saves the result for later reads and runs and does not erase the prior list on failure. A changed provider, URL, or protocol invalidates old discovered choices for that connection. Connection deletion also removes its saved discovery list.
- For a discovered ID unknown to Pi, the backend exposes a conservative text-only definition: 8,192-token context, 2,048-token maximum output, and no reasoning. It is marked unverified. Agents may select it and make basic calls; the endpoint may still reject the request. Registered definitions supply their own metadata. A model absent from both the current registered catalog and the saved discovery list cannot be selected for a run.
- Agent config saves provider connection and backend-supplied model ID directly. A run uses only the `modelOptions` entry for the selected model. Defaults apply per field: reasoning uses the model's effective default level; omitted temperature, maximum output, and context budget are omitted from the Pi call, so the provider or model default applies. A saved scale level is sent as the model's mapped level; a mapped `off` sends a request with thinking disabled.
- The selected model's entry must fit that model: reasoning is set only for a reasoning-capable model, `maxTokens` does not exceed its maximum output, and `contextBudget` does not exceed its context window. A scale level the model lacks is not a misfit; it is clamped as above. A misfit, for example a reasoning level saved for a model without reasoning, is reported as an agent issue and prevents runs until edited; the backend does not substitute another value. Entries for unselected or no-longer-listed models are kept, are not checked against model metadata, and do not block runs. Because each entry fits only its own model, selecting another model never creates a conflict.
- The agent list covers agents outside teams only. A team member's settings issues appear in its team view from the same checks, supplemented by team/harness readiness checks, and its run resolves its settings like an agent's, with the member's record revision as the snapshot's agent revision.
- Before accepting each run, the backend resolves a consistent, independent snapshot of app, agent, selected connection, discovered model data, and selected tool and prompt definitions. The run uses it until completion; edits affect the next run. A run does not hold a lock on editable config. The snapshot includes source revisions and the decrypted key, which is never returned to the frontend.
- App and UI consumers resolve at their own read points. Editing config does not rewrite message history or an active run's context.


- Invalid data, unsupported fields, stale revisions, and missing records fail explicitly without changing the previous record. A discovery failure preserves the previous cached model choices and reports the error.
- An agent config that includes `workspaceId` is rejected as an unknown field and leaves the record unchanged.
- An agent or team member with no selected model, a missing connection or model, or a selected-model entry that does not fit the model cannot start a run; its proposed input is not accepted as a run. There is no silent fallback model.
- A provider credential or endpoint failure during a run is a run error. A stored key is encrypted at rest, never returned by reads or logged, and decrypted only on the backend. Invalid deployment encryption configuration prevents saving or using saved keys.
- An active run continues with its snapshot if its source records are edited or deleted. A later run may fail resolution. Storage failure makes new reads, edits, and resolutions fail rather than serving a stale result as current.


- Model IDs originate from registered provider catalogs or endpoint discovery and are selected by the agent; there is no editable global model profile or global reasoning allowlist.
- A provider's registered models can be listed offline. Endpoint discovery requires a compatible model-list API. Unknown models have conservative metadata and no verified reasoning support. Listing a Pi definition or endpoint-advertised ID does not prove that the configured credentials can call it; a model call establishes that.
- Context budget is snapshotted now; automatic compaction remains a later context-management feature. The model's hard context window is backend metadata, not an editable agent field.
- Agents and team members resolve model and prompt settings alike. Workspace members require empty catalog tool selections because their harness supplies executable tools; the team adds this readiness rule. A run snapshot carries no workspace; a member's workspace belongs to its team.
- Existing saved model profiles and agent selections are migrated to connection/model selections where their model can be resolved. Unmappable selections remain incomplete and surface an issue, so users can correct them without a silent model substitution. A `workspaceId` stored in an agent config, which a version that bound agents to workspaces wrote, is ignored when the config is read, and that agent works as an agent without a workspace.
- Agent-wide `callOptions` from earlier versions are dropped when read: existing agents start with default model-call settings for every model. Writes no longer accept `callOptions`. A stored entry reasoning outside the shared scale (`minimal` or `max` from the earlier per-model levels) is dropped when read, so that model uses its default reasoning.
- The shared scale is the user-facing contract; the level sent depends on Pi's current model metadata, so a Pi upgrade can change which level a scale step sends without changing saved config.

## Constraints, specifications and requirements

1. An editor saves an OpenAI provider connection with a key. The API returns `keyConfigured: true` but never the key. Pi-known OpenAI models appear in its list; an agent selects one and saves reasoning and output limits in its own config.
2. A compatible custom endpoint returns a new model ID. Refresh saves the ID. An agent can select it on a later page load without another provider request; the UI labels its conservative capabilities unverified.
3. A failed refresh leaves the last successful discovered list available. Changing the connection URL makes that old list unavailable until the new endpoint is refreshed.
4. Editing the connection key or the agent's temperature during a run leaves that run's requests unchanged. Its next run uses the new snapshot.
5. A selected model disappears from both Pi and the connection's current discovery list. The agent remains editable, but a new run reports the missing model.
6. An Anthropic-compatible connection uses Anthropic Messages. Refresh reads all pages from `/v1/models` with the Anthropic API version and key, and an agent can call a discovered model through Pi's Anthropic adapter. The editor uses the provider root URL; it does not require a model ID.
7. A DeepSeek connection with the Anthropic Messages protocol and `https://api.deepseek.com/anthropic` can select a Pi-known DeepSeek model. A run sends an Anthropic Messages request to that endpoint, even though Pi's default definition of that model uses OpenAI Chat Completions.
8. Model A supports `off, low, medium, high`; model B supports `off, high, max`. An agent saves `high` and `maxTokens: 64000` for A, switches to B and saves `xhigh`, then switches back. A runs with `high` and 64,000 output tokens again; B keeps `xhigh`, sent as `max`, with default output. A newly selected reasoning model C with no entry runs with `off` (or its lowest level if it cannot disable thinking) and omits the other options.
9. Agents 1 and 2 both select model A. Agent 1 saves `high` for A; agent 2 still runs A with its own settings.
10. Model A above has no `xhigh`; saving `xhigh` for it is accepted and sends `high`. Saving `minimal` or `max` is rejected. Saving `low` for a non-reasoning model is reported as an unavailable reasoning level and blocks runs until cleared.
11. An agent config saved with `workspaceId` is rejected as an unknown field. One stored with it reads without it and keeps working. A new agent with a provider and model is ready and has no workspace.
12. A team member's settings are validated by the same rules: a reasoning level the model lacks is clamped, `minimal` is rejected, and a missing model is an issue that stops the member's run. The agent list does not include team members.

13. A connection selecting `modelflare` lists registered models including `claude-haiku-5-5` offline with documented reasoning support and limits. Another provider does not inherit these models by matching a connection label. Modelflare image/video and decision-only models are not agent model choices.
