# Operations

## Purpose, responsibilities and boundaries

Operations runs this project on the operator's host in two independent environments: development from the current checkout and deployment from a committed Git revision exported to replaceable temporary storage. Both environments use a dedicated MySQL service belonging to this checkout, isolated from another branch's legacy service. Development and deployment have separate databases and encryption keys. Operations owns lifecycle CLIs, environment configuration, database service/provisioning, and the deployment static/streaming frontend host.

Operations does not own application schemas or records (the backend migrates and owns them), the meaning of provider credentials, or user project/workspace files. Deploying application source never copies or moves workspace files.

## Interface contract

**Purpose and supported interactions.** The operator uses three shell entry points:

- `scripts/dev.sh`: `init`, `start`, `stop`, `restart`, `status`, `logs [backend|frontend]` for checkout-based backend/Vite development.
- `scripts/deploy.sh`: `init`, `deploy <git-ref>`, `update [git-ref]`, `start`, `stop`, `restart`, `status`, `logs [backend|frontend]` for host deployment.
- `scripts/database.sh`: `start`, `stop`, `status` for this checkout's dedicated MySQL service and database provisioning.

All user-configurable Operations settings for both development and deployment come from one configuration file in the project root (`operations.config.json`). The scripts must not read environment variables, dotenv/env files, or other configuration locations as alternate or overriding inputs; in particular, they must not write to or alter the caller's environment or another service's environment/configuration. The root config is local and secret-bearing, so it must be excluded from version control with an example/template containing non-secret defaults. Node.js 22.19+, npm, Git, tar, curl, ps and Docker Engine are required as applicable; Docker Compose is not required. Development defaults to loopback backend/frontend ports 3000/5273; deployment defaults to 3001/5274. Occupied ports fail rather than taking over unrelated processes. Deployment source root defaults to `/tmp/rsi-agent-deploy`; the config file supplies the Operations state directory, deploy root, ports, database/service identity and separate environment encryption keys. The exact schema and bootstrap behavior are implementation details, subject to preserving the single-file-only configuration contract.

**MySQL container contract.** The project-root config supplies the fixed container name, image, host port, database root credential, named volume name and mount path. Operations uses plain Docker Engine commands (`docker run`, `docker start`, `docker inspect`, `docker stop`, and narrowly scoped `docker exec`) and does not generate or consume Compose configuration. Container and volume identities are explicit, stable, unique to this project checkout and distinct from the other branch's legacy service. Before use, scripts inspect existing resources and verify ownership/configuration (including the expected container labels, image, port binding and volume mount); on mismatch or identity collision they fail without taking over, deleting, recreating, or attaching to the resource. A checkout move requiring a new identity must be explicitly configured; scripts must never silently derive a new identity and bind an old volume or silently adopt an unrelated resource.

**Observable effects and lifecycle.** Development and deployment run independently and connect to separate databases on this checkout's dedicated MySQL service: `rsi_agent_dev` and `rsi_agent`. The service is one explicitly named Docker container with one explicitly named persistent volume, distinct from the other branch's legacy service. It is started and inspected with plain Docker Engine commands; no Compose file or Compose CLI plugin is used. First initialization creates empty databases; legacy records are neither copied nor modified. Development and deployment receive their database URLs, encryption keys, ports and other tunable settings only from the project-root Operations configuration file; inherited `DATABASE_URL`, `CONFIG_ENCRYPTION_KEY`, port variables, shell environment, dotenv files or legacy environment files must not redirect either environment. Scripts must not modify or export configuration back into the caller's environment and must not edit another service's environment/configuration. The local config contains secrets and must be permission-restricted and excluded from commits; a checked-in example may document keys and safe non-secret defaults without supplying real secrets.

Before any Docker mutation, Operations verifies the configured container and volume identities and confirms the container belongs to this project with the expected service settings. Existing mismatching resources cause a safe refusal; the scripts never remove or replace containers/volumes automatically. Database provisioning uses only non-destructive create/grant operations.

Development `start` ensures this checkout's MySQL service is healthy and development database/account provisioning is complete, then starts backend and Vite and checks readiness. Deployment initialization preserves existing deployment configuration/key before initializing both environments. `deploy <git-ref>` resolves a locally available committed revision, exports a separate temporary release, installs locked dependencies and builds before stopping the current deployment; uncommitted edits and environment files are excluded. It launches the compiled backend and a host frontend serving built assets while proxying API, uploads and SSE to the backend. Readiness precedes active-release selection. `update [git-ref]` selects the requested local committed revision (default: checkout committed HEAD); it does not fetch, pull or switch branches. Starts can rebuild the selected exact revision if temporary build files were removed. App stops do not stop either database service; only explicit database stop stops this checkout's service, preserving its volume.

**Failure behavior and lifecycle guarantees.** Invalid refs/configuration, missing dependencies, occupied ports, corrupt/missing keys, service health/provisioning errors and readiness failures return nonzero without logging secrets. A build failure leaves the running deployment intact. A launch failure stops newly launched processes and attempts recovery of the prior running release; recovery failure is explicit and does not roll back database migrations. Lifecycle mutations are serialized/refuse concurrency. Process termination requires positive process identity; stale/reused PIDs or ports never justify killing foreign processes. Status is read-only; logs do not require a running database. Failed development startup stops only processes started by that attempt and leaves both MySQL services and deployment intact. Failed DB startup does not stop either service. Provisioning never drops/truncates/resets databases, rotates deployment credentials, or copies data. Explicit database stop affects only this checkout's service and preserves its volume.

The deployment frontend keeps API/upload responses streaming rather than buffering whole bodies; SSE remains live and disconnects close proxy requests. Local readiness requests bypass shell HTTP proxy settings.

## Constraints, specifications and requirements

- Deployment refs must resolve to a local committed revision containing required scripts and host frontend entry; historical source must remain locally available to rebuild. No automatic fetch, branch switch, or inclusion of uncommitted changes.
- Deployment source/build files are replaceable and must not contain deployment keys or user workspaces. Durable state, logs, release selection and user workspaces remain outside the temporary source tree.
- All tunable development/deployment/database-service settings are loaded exclusively from one project-root Operations config file; no environment variables, dotenv/env files or secondary config sources act as inputs or overrides. The scripts do not modify the caller's environment or another service's configuration/data.
- The root config contains secrets, is excluded from version control and is permission-restricted; a non-secret example/template documents its schema and defaults.
- Development and deployment use distinct encryption keys and databases. The deployment key is retained across config initialization, but cannot restore records absent from the new database.
- The dedicated container and named-volume identity must be unique to and stable for this checkout, distinct from the other branch's legacy service, and must not silently attach to an unrelated volume if the checkout moves. Identity is explicitly configured; collision/move behavior must fail safely.
- Repeated service starts/provisioning preserve both databases' data. Stopping either application leaves both MySQL services available. Explicit service stop is scoped to this checkout and preserves its volume.
- Process management must not kill foreign processes; concurrent lifecycle mutations are refused; secrets are not logged or placed on process arguments.
- Both applications bind to loopback by default. No TLS, public exposure, boot supervisor, automatic update, app schema change, destructive data reset, or legacy-service mutation is introduced.
- Database separation does not isolate manually shared project directories. Users should stop both applications before intentionally stopping this checkout's MySQL service.
- Acceptance: initialize with legacy data present and verify legacy service/data remain untouched while this checkout's two databases start empty; start both apps and verify each UI reaches its own backend; stop/restart one app without affecting the other app or either database service; test foreign occupied ports, build/readiness recovery, rebuild after temporary source deletion, streaming SSE and image uploads.

## Implementation mapping

`scripts/host-common.mjs` provides shared durable paths, environment validation, process identity, locking, logging and readiness. `scripts/develop.mjs` and `scripts/dev.sh` manage development lifecycle. `scripts/deployment.mjs`, `scripts/deploy.sh` and `scripts/serve-frontend.mjs` manage release selection and host serving/proxying. `scripts/database.mjs` and `scripts/database.sh` manage the checkout-specific MySQL lifecycle and provisioning. `backend/compose.yaml` contains the legacy service configuration and must remain unaffected; Operations must not use Docker Compose. `scripts/test` contains lifecycle tests.
