# Operations

## Purpose, responsibilities and boundaries

Operations owns project environment management and lifecycle: development environment setup, required toolchain/dependency installation, development launch configuration and processes, deployment build/release/process management, and supporting database-service initialization and lifecycle. Backend Core owns application records/schema; Storage owns application database access. Operations manages database service infrastructure and connection configuration, but does not interpret or migrate application business data.

## Interface contract

Project configuration is aggregated in one private `rsi.config.json` file. It is the single source for project-level application, development, deployment, environment/toolchain/dependency, and supporting database-service settings; commands do not require a second private configuration file or hidden configuration source. Environment-specific values remain grouped and isolated within that file, and commands keep settings in child processes, preserve caller/global environment and refuse unrelated occupied ports/processes. Operations owns setup and documented installation/verification of the development toolchain and dependencies, using the project’s declared dependency manifests and lockfiles rather than inventing unpinned alternatives. Each environment explicitly configures one positive safe-integer contextCompactionThresholdTokens and the harness permission switch; the example configuration supplies initial values. The same value controls both Agent checkpoints; do not couple it to per-model stored contextBudget or add separate trigger thresholds.

Operations owns the development environment lifecycle, including setup, dependency readiness, initialization and configuration of this project's isolated development database service, plus explicit service start/stop/status operations. Each project owns one MySQL service shared only by its own development and deployment environments, using distinct schemas, application accounts and encryption keys. The service image, Compose identity, container, network, volume and host port are configuration inputs. The service uses a project-specific Compose identity, storage volume, network and credentials; it must not reuse, stop, reset or mutate another project's service or data. Its host port is explicitly configured by this project's private configuration and checked for conflicts. Existing database services remain untouched. Development app configuration points to the project-owned service on the configured loopback host/port. Database service management does not interpret or migrate application business data.

Development and deployment settings and databases remain separately configurable. Project commands manage development and committed host deployment. Deployment builds an exported local commit before switching app processes, preserves the current release on build failure and attempts recovery on launch failure. Stopping an app preserves its database service/data. Existing old compiled release entries remain startable for recovery after source migration. Configuration initialization uses the checked-in example and generates fresh secrets; it never silently imports another checkout, legacy env files, ambient application variables or shared state. Runtime Compose configuration is generated from this single configuration, not maintained separately. Process records, lifecycle locks and release manifests belong to the configured project and state paths. A deployment manifest from another checkout must be refused. Database provisioning and connection checks precede application startup.

For this migration only, explicitly copy the existing RSI deployment database once into the isolated team-work service. Preserve the source database and service, existing team-work development data, and the deployment encryption key needed to decrypt copied credentials. Verify the copy before starting the new deployment. This is a one-time snapshot, not ongoing synchronization; project directories referenced by copied workspace records are not duplicated.

## Constraints, specifications and requirements

- Preserve existing accepted observable behavior, record formats, revisions/cursors, API payloads and lifecycle guarantees during this migration.
- Refusals and failures remain explicit. Database transactions provide their agreed atomicity; executed tools/filesystem operations may leave earlier effects on failure.
- This document is the design; matching implementation context documents exact inputs, outputs, effects and usage.
