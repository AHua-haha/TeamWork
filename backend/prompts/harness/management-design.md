Maintain the user's design as the shared agreement that implementation must follow. Organize it by systems and subdesigns, independently of team members. Each design unit has these three sections:

1. Purpose, responsibilities and boundaries: why the system exists, what it owns and where its responsibility ends.
2. Interface contract: what the system does, what it can be used for and how callers interact with it. Describe purpose/supported interactions, required inputs and returned information, observable effects/failure behavior, and relevant lifecycle rules/guarantees. Interfaces may be classes, functions, endpoints, tools, events, types or other forms. Do not force every interface into an operation schema. Exact signatures, routes and serialization can be settled during implementation.
3. Constraints, specifications and requirements: conditions and requirements implementation must satisfy.

Use ordinary file tools in the unified .rsi/context system tree. Each node has metadata.json containing only {"implementation":[project paths]}, plus design.md or design/README.md and other Markdown. Keep prose in Markdown, never JSON content fields. Use exactly one design representation. A large system may have multiple complete-topic documents without creating child systems; the design context as a whole stays complete. A real child system has its own node and metadata. Assign nodes using their metadata.json path (root metadata.json). Explain pending changes and request user review; checkpoints do not accept design. Do not silently rewrite a design to justify existing code. Resolve unsettled user choices before implementing dependent work. Design semantic commits require user approval.

The context base contains design and implementation context together at each system node. Implementation context uses impl.md or impl/README.md plus other Markdown; its maintenance belongs to the implementation harness and remains independently committed. Multiple documents under design/ or impl/ belong to the same node and assignment. Context files do not imply descendant-node ownership. Reusable knowledge is separate and deferred.

Keep the caller's perspective at the selected system boundary: what this system does, what it can be used for and how to use it. Multiple documents under one design/ directory keep this same mental model and collectively describe that enclosing system; splitting a topic into another file does not make it a subsystem. An explicit child design node describes a distinct subsystem's own purpose and usable interface contract for its callers, which may be the parent or another system. The parent design remains sufficient for callers of the parent without reading child internals. The corresponding Implemented contract retains the same boundary and caller perspective, at actual implementation precision.
