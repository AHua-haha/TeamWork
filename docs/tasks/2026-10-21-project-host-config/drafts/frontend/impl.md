# Frontend implementation

## Contract

[Frontend design](design.md). The agent client owns backend requests, Pi data, synchronization and recovery. The assistant-ui adapter derives display messages and actions without becoming another source of history. The workspace client owns workspace, current-design, team, project-file and context-base requests and the context change feed; the workspace panel derives its current Design/Team and Changes tabs, trees and file viewer from those responses. It uses the operations of the [Workspace design](../workspace-agent/workspace/design.md), the [Team design](../workspace-agent/team/design.md), and the [Context base design](../workspace-agent/context-base/design.md).

## Responsibilities and decomposition

- The agent client is a UI-independent TypeScript module. It owns an immutable snapshot, a subscription API, SSE parsing, completed-record reconciliation, live Pi partials, run/connection state, and commands.
- The assistant-ui adapter is a React integration that converts each client snapshot into `ThreadMessageLike` values and wires `ExternalStoreRuntime` callbacks.
- `ConfigClient` exchanges app, connection, model-choice, catalog, capability, agent-list, and per-agent config records in the backend's JSON format. API keys are not retained in client records.
- `routes.ts` parses and builds the address: `?workspace=<id>`, `?agent=<id>`, `?page=providers`, and the home page. It is pure, so tests cover it.
- `App.tsx` owns the current route, two-level shell, the workspace, solo-agent and connection navigation lists, add-workspace and new-conversation actions, inline renaming of solo conversations, the panel's open and expanded state, and the guard that confirms leaving a workspace page with unsaved files. The rail collapse state and the panel's state are view-only; the route remains in the URL. It renders `WorkspacePage` for a workspace route and `SoloPage` for an agent route.
- `ChatPage.tsx` composes one conversation from an agent ID and a settings control: the agent client, the assistant-ui runtime, and `Conversation`. SoloPage uses it for private solo conversations.
- `SoloPage` gives it the config hook for an agent. `WorkspacePage.tsx` loads the workspace and its team, mounts GroupChat for the workspace’s shared timeline, and mounts the panel beside it.
- `useTeam.ts` owns a workspace's team: reading it on focus, timeline updates and every three seconds during any member work. Superseded responses are ignored. MemberInspector reads accepted member/config/harness data without mutation controls.
- `ProvidersPage.tsx` owns the provider overview cards and add/edit dialog. Cards read model choices and refresh them through the config client. The dialog manages a write-only key replacement or explicit clear.
- `ComposerSettings.tsx` owns the cross-connection model picker, compact selected-model view, folded search field, pill reasoning slider, folded More settings section, save state, and Send gate. `model-selection.ts` identifies models by connection plus model ID, reads and replaces one model's `modelOptions` entry, derives the effective reasoning level and its clamped sent level, counts customized fields, and reports per-field misfits against model metadata. A model switch changes only the selected IDs, so every model keeps its own entry.
- `useAgentConfig.ts` owns a current agent-config record and revision-aware saves. Its optional expected revision prevents a stale composer draft from being applied to a newer record. `initialize` creates a missing record from empty defaults.
- `Thread.tsx` renders solo conversations and their headers, and the issue banner, and mounts the composer control. A tool card for `send_message` is headed by its recipient. `styles.css` owns the light desktop and mobile layouts, including an overlay sidebar and a slide-over panel on narrow screens.
- `WorkspaceClient` exchanges workspace, project-file, and context-base records in the backend's JSON format, and raises `BackendError` with the backend's status and code. `ContextFeed` follows one workspace's change records. It owns an immutable `{seq, connection, error}` snapshot, a subscription API, record listeners, envelope validation, and reconnection; it does not depend on React.
- `WorkspacePanel.tsx` owns the panel for one workspace page: loading the workspace with its overview, the panel bar, and one `WorkspaceView`. A view owns the feed, the context overview, the permanent Design, Team, Changes and Files tabs and the file tabs and which one is active, the tree column with both trees and the find filter, the new/move/delete dialogs, and the close-tab guard.
- `TeamTab.tsx` renders active members and their active details only; `ChangesTab.tsx` owns read-only design/member review and separate activation. MemberTree attaches member cards to design-file rows; selected active details compose MemberInspector; WorkspaceModelsDialog edits workspace initialization choices.
- `FileTree.tsx` owns `useFolders`, which loads open folders lazily and re-reads them per reload generation, and `FolderTree`, which renders one source's entries with per-entry actions. It also holds the path helpers.
- `FileView.tsx` owns one open file, in its tab: a reducer over the loaded version, the draft, an incoming conflicting version, and the deleted state; the breadcrumb header with icon actions; Preview/Text; save, discard, copy, reload; the feed subscription for a context file; and `FileHistory`, which pages versions and selects one to view or restore.
- `Glyph.tsx` draws the small line icons used by the panel, the viewer, and the conversation header.
- `markdown-parser.ts` parses the supported Markdown into a block and inline tree and resolves links. `Markdown.tsx` renders that tree as React elements.
- `WorkspaceDialogs.tsx` owns the modal `Dialog` frame, the create-workspace, path, and confirm dialogs, and `useSubmit`, which keeps a dialog open with the backend's message when its action fails.

The app, prompt, tool, and advanced agent configuration editors have no visible page. Their backend data and APIs remain; model and settings writes spread the existing agent record and preserve fields not edited in the composer.

## Coordination and data flow

On mount or refresh, the client opens a run-scoped SSE follow request. Completed records fill its ordered history. The `sync` event establishes that the history is current, then compact frames incrementally update a local partial by block index. A `message` event supersedes the partial with the same identity. Gaps and reconnections clear affected partials; an unexpected EOF retries the follow operation using the last completed position. `end` closes the connection and no periodic request is scheduled. A submit POST carries only new user content; its accepted run ID starts another follow request. Leaving a conversation disposes only that frontend follow client; the backend run continues and resynchronizes when the user returns.

App loads workspaces, solo agents (`GET /agents`, which leaves out team members), and connections on mount and refreshes those lists on window focus. Creating a solo conversation calls the create-agent endpoint, initializes an empty agent config, and opens its chat. Adding a workspace opens the create dialog; the created workspace joins the list and its page opens. Renaming fetches the latest agent config and updates only its name at that revision; the mounted conversation refreshes its config afterward. The provider sidebar contains shortcuts to cards on the single overview page.

**A workspace page.** WorkspacePage reads the team, composes GroupChat and WorkspacePanel, and preserves discussion references. GroupClient replays `/team/chat/timeline-follow` changes using a contiguous change cursor, keys sections by entryId and sorts by persisted display position. POST acknowledgements merge by revision without advancing the cursor. EOF reconnects; protocol errors stop with Retry. Accepted sends clear only unchanged drafts and the exact submitted reference. Team status refreshes on changes and during work.

GroupChat renders right-side input bubbles and open member responses with transparent backgrounds and a light header divider in a centered reading column. Outside avatar/name stacks occupy the left member gutter and right user gutter; user bubbles contain only message text and have no extra middle-column inset, aligning their right edge with the member response container. Shared user-bubble typography/padding variables derive both avatar layout diameters from the one-line bubble height (about 47.1px). A center-origin 80% transform shrinks the visible circles to roughly 37.7px without changing centers, names or message geometry. The grid keeps their layout slots top-anchored for longer messages; derived gutters preserve equal 12px desktop/8px narrow slot gaps; visible circle-to-response gaps increase equally by half the size reduction. Member entries use two grid rows: group-run-area places the pills outside in row one, aligned with the response container’s left edge, with 8px bottom padding and no separate bottom margin or border. The identity and response container occupy row two so the avatar remains anchored beside the body. group-run-card encloses expanded activity and final content, with a transparent background, a 1px solid #e9ede8 top divider and no other border or rounded corners, 18px default top padding and 20px side/bottom padding (14px narrow). When a folded final starts with a paragraph or heading, :has selects that container and removes its default top padding. The first block instead gets calc((var(--group-avatar-size) - 1lh) / 2 - 1px) top padding, using its own computed line height and compensating for the divider. This puts its first-line center on the avatar reference center without moving avatars or changing heading typography. Empty pending response containers retain at least the reference slot height. There is no shadow or negative pill-row inset. Initial response content has no extra leading margin; expanded work has spacing before final/terminal content. group-run-area keeps its 6px pill gap and vertical center alignment. Shared group-run-pill styling gives the passive status/duration/start tag and separate Work button matching 24px capsule geometry. The borderless status tag uses data-status for #f0f6f0 completed fill with #52765a status text, #faf1f0 failed/interrupted fill with #a3635c status text, and #f5f6f5 fill with #727a73 text otherwise. Duration and start time inherit #727a73. Work uses a transparent background, #e7eae6 border and #727a73 text, with padding compensated for the border; hover uses #f1f3f0 and darker text, while aria-expanded=true uses #eef1ed and dark gray text. Avatar/name identity colors are retained. The Work button alone owns click/keyboard disclosure, aria-expanded and the controlled history ID; its standard 12px Glyph chevron rotates downward when expanded. There is no tinted header band; the divider is the response container’s top border, exactly aligned with the member avatar reference slot top. The shared avatar center rule matches the user bubble; expanded work remains below the divider without moving it. Expanded work is transparent and untitled. Narrow capsule text and composer controls wrap as needed. styles.css adds the derived gutters and response padding to timeline and composer offsets to preserve the 800px text/composer maximum and alignment. MemberResponse owns an AgentClient with the entry’s private start boundary and selected run. It follows throughout active work, regardless of disclosure, and reads completed work on demand. runActivity filters run/range, pairs tool results, ignores thinking, groups consecutive tools, and excludes accepted final blocks by exact reference and content indices. Acceptance folds Work once; later updates preserve the user’s choice. Private errors stay local. Terminal entries remain inspectable. Group-chat avatar model settings use the dedicated member model API; the shared composer uses mentions and group Stop.

Each provider card fetches its backend model choices. Refresh invokes endpoint discovery. Add and edit use the same focused dialog, but edit starts from the connection record returned by the backend. Selecting a known provider preset fills its Pi endpoint and default protocol; the editor may choose another supported protocol and URL. A blank key input means keep the saved key; an explicit clear sends `null`. The dialog never receives the raw saved key. Delete uses the revision-aware endpoint after confirmation.

The composer loads the connections and each connection's choices. Its search icon reveals an initially folded field and the grouped model list. With a selected model, the list starts collapsed; clicking the model summary expands it, and selecting a model folds it again after a successful save. Selection writes `connectionId` and `modelId` together without prompting; switching back shows that model's earlier entry. The popover header shows the effective reasoning level in large text. A transparent native range input over a compact 22px pill track uses integer stops mapping to the backend-listed levels, which are the five-level scale for every reasoning model; pointer release, a reasoning key, or blur after a staged change commits it. Without a saved level the slider shows the backend default and writes nothing; choosing the default while no saved value misfits also writes nothing. `clampedTo` reads the model's `reasoningSentAs`, and the scale row shows "Sent as …" between the end labels when the displayed level is clamped. Zero levels show "No reasoning"; a level saved for such a model is marked and offers to clear it. More settings is keyed by model and starts folded on each open, labeled with the number of customized fields and a needs-attention marker for misfits. Its maximum output tokens, temperature, and context budget inputs show Default with the model's limit when unset, validate staged text against the model, can each be cleared to Default, and save together; context budget is described as stored for future context management. For solo conversations, unsaved More settings edits, a pending, failed, or invalid save, or a selected-model misfit gate sending; group admission validates persisted member readiness. A stale revision reloads the latest value for review. The backend still resolves the config snapshot at run start.

### Workspace panel

App keeps the panel's open and expanded state and passes it to the mounted `WorkspacePage`, which is keyed by workspace, so the state carries across workspaces while each workspace gets a new panel. The page header's **Show design, team and files** button opens the panel and is shown only while it is closed; the panel bar's buttons expand or restore it and hide it. At 760px and below, opening it also closes the left sidebar. The panel mounts its contents on first open and stays mounted while closed (`aria-hidden` and `inert`), so its tabs and drafts survive hiding. A scrim button behind the slide-over closes it on narrower screens.

The panel's workspace is the one in the address; the page reads it with its context overview, with Retry on failure, and passes it to one `WorkspaceView` keyed by the workspace. A solo conversation mounts no panel.

The panel bar holds the permanent Design, Team, Changes and Files tabs, the file tabs, a "+" that shows the tree and focuses its filter, the tree toggle, and the panel actions. The active surface is design, team, changes, files or a file key; Design is initial and the fallback after the final file closes. Every open tab keeps its `FileView` mounted and hidden when inactive, so a background tab keeps its draft and feed subscription, and the Team view's content is rendered from the page's team state. The tree starts hidden and can be toggled from any surface; Files reveals it. A tab is created once per file with its own `onDirty` and `onMoved` handlers, so its view's effects keep their subscriptions. The view keeps the set of dirty tab keys, marks those tabs, and reports whether any is dirty; App keeps that in a ref, and its `navigate` and `popstate` guards confirm leaving the workspace page with **Leave with unsaved changes?** A `popstate` that would leave pushes the current URL back while the dialog is open. A design reference in a member card selects the current Design view. Implementation links open files or reveal mapped directories in Files.

`WorkspaceView` starts a `ContextFeed` after the overview's `seq`, so the feed replays only later records. The feed sends `follow?after=` and validates each envelope's version, workspace, and type. It applies a record only when its `seq` is exactly the next one, and checks that `sync` equals the applied `seq`. A `stream_error`, a closed stream, or a dropped connection reconnects after the last applied `seq`, with backoff `min(500·2^min(attempt, 4), 8000)` ms that resets at each `sync`. A protocol error or a 4xx response stops the feed with an error. The snapshot's `seq` advances before record listeners run. The view coalesces records for 150 ms, then reloads the open context folders and re-reads the overview, keeping a response only if its `seq` is not older. Retry re-reads the overview, reloads the trees, and starts a new feed from that `seq`; the open tabs and their drafts stay.

`useFolders` keeps the set of open folders and a reload generation. Each open folder is listed once per generation; a later response for an older generation is ignored. A 404 for a non-root folder closes it, which handles folders that moved or were deleted. `FolderTree` sorts folders first and shows a note when the listing is truncated. The find filter waits 200 ms, then calls both find operations together, ignoring superseded responses.

Opening a file expands its ancestors and activates its tab, or adds a tab when the file is not open; at 760px and below it also hides the tree, which covers the viewer there. Closing a dirty tab asks to discard its changes; closing the active tab activates its neighbor. New file saves empty content with `baseRevision: null`, then opens the backend's returned path in a tab in Text with the editor focused; a project create also reloads the project tree. Move expands the destination and re-targets open tabs from the response's `moved` pairs, so tabs follow even while the feed is disconnected. Delete closes the clean tabs of deleted files; a dirty tab stays, and its view marks the file deleted when the feed record arrives. The trees and the open tabs also learn about the result from the feed record.

`FileView` reads the file and dispatches the result to its reducer. A newer read replaces the view when it is clean, or when the new content equals the loaded content or the draft; otherwise it is held as `incoming`. A per-view read token discards stale responses. Save sends the loaded revision, or `null` after a delete. On `stale_revision` or `file_exists` it keeps the draft, shows the conflict message, and reads again, which surfaces the newer version as `incoming`. **Save mine over it** saves with the incoming version's revision. For a context file, the view listens to feed records: a move from its path calls `onMoved`, which re-targets the same view; a delete marks it deleted; any other change to its path reads again. Paths compare without letter case. A dirty view installs a `beforeunload` warning and reports dirtiness to its tab, and reports clean when it unmounts. Ctrl/Cmd+S saves. The header shows the breadcrumb (workspace, Context base for a context file, the folders, then the name) and icon actions: Preview and Plain text, history or Reload, Copy, Rename and Delete for a writable context file, and Discard and Save when there is something to save. The footer shows the version's time, size, author, and reason.

History pages with `before=next`. Selecting a version reads it by revision and shows it read-only; selecting the current revision returns to the current view. Restore saves the version's content against the current revision with the reason `Restored the version from <time>`, then reads again. Restore is disabled while the draft is dirty.

Preview parses the content into blocks and inlines and renders them as React elements, so raw HTML stays text. `externalHref` accepts only `http`, `https`, and `mailto` links, which open in a new tab. Another URL scheme renders as plain text. A relative link calls back to the viewer, where `resolveLink` drops any query or fragment, decodes the path, and resolves `.` and `..` against the linking file's folder. It returns `null` for absolute links and for links that leave the file's root (the context root for context, the workspace for a project file); otherwise the panel opens the resolved path in the same source.

## Decisions and constraints

Vite serves React and proxies `/agents`, `/config`, and `/workspaces` to the backend during development. The client uses browser `fetch` and parses the backend's SSE envelopes without depending on React. Backend protocol types are kept in the frontend client boundary with Pi AI types; runtime checks reject malformed envelopes. Assistant UI 0.15 uses `useExternalStoreRuntime`. The display converter associates separate Pi tool-result records with preceding tool-call parts and preserves source records in the client. CSS supplies a light palette for all states and viewport sizes. No frontend tool execution or model-context submission is enabled.

The secondary Config panel lists provider connections as shortcuts because Providers is the only config page. Larger cards use one readable column; the model list expands inside a card. On mobile the secondary panel overlays content and starts closed. Closing it does not change the URL or the active agent run. Hidden prompt, tool, and app editors are not replaced by another general settings view; model-call settings live in the solo composer popover; Team cards inspect member settings and Workspace models edits initialization profiles. The Providers page holds connection information only.

The picker labels duplicate model IDs and names with their connection, never assuming a model ID is globally unique. The slider's integer step prevents unsupported intermediate reasoning values from reaching the backend. The frontend displays the backend's sent-level mapping and does not compute clamping itself. A provider model list does not prove the configured credential can make a model call.

The panel belongs to a workspace page, not a route of its own: the page is a flex row of the chat and the panel. Open, the panel is `clamp(480px, 52%, 980px)` wide; expanded, it takes the whole page and the chat is hidden. The viewer fills the panel and the tree is a 280px rounded column floating at its right edge. At 1100px and below the panel becomes a fixed slide-over (`translateX`) of `min(880px, 100vw − 64px)` with a scrim, expanded to `100vw − 64px` with the chat still visible beside it, and the tree column is 250px. At 760px and below the panel is `100vw − 56px` without Expand, and the tree covers the viewer. Reduced motion disables the slide. Drag-resizing is not offered. The workspace comes from the address, not from browser storage, so a workspace opens on any device.

The team is read, not followed: the backend has no change feed for it, and a polling interval of 3 seconds while any team member runs keeps the cost small. The sidebar lists workspaces and solo agents separately because the backend keeps them apart: `GET /agents` returns no team member, and a workspace's lead is reached through its team. The lead is initialized from workspace models; activated member files remain team-owned; the dedicated member model API stores user preferences used by avatar controls.

`ContextFeed` and the agent client share the SSE parser, `BackendError`, `json`, and `waitForRetry`, but the feed is a separate class because its stream never ends and its position is a workspace `seq`, not a run. Each tab owns its file's draft, conflict state, and unsaved-changes report; the panel only aggregates which tabs are dirty. Tabs are kept in memory and are not persisted or reorderable. The Markdown subset is hand-written, so the frontend adds no Markdown or HTML-sanitizing dependency, and parsing never produces HTML strings. Context paths compare without letter case, matching the backend; project paths compare exactly. The frontend shows the backend's error messages and does not duplicate its path rules.

## Workspace models and member inspection
