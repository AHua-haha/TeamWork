# Agent harness implementation

## Contract

[Harness](design.md) defines the three purpose bases, common tools, protected acceptance, node-based context/code authority and independent staged history. Member activation is a separate user-only idle operation owned by the team.

## Responsibilities and decomposition

HarnessService composes accepted designs, fixed bases, scoped files/history and Bash. HarnessHistory owns worktrees, Git objects, staging repositories, checkpoint indexes, accepted refs and design acceptance pointers. The [team](../team/design.md) owns stable active member identity/content; [runtime](../../agent-runtime/design.md) owns the model loop and tool cancellation. [Design parts](../context-base/design-parts/design.md) resolve accepted semantic designs.

Reusable file adapters and one Bash adapter receive runtime identity; policy is resolved by harness services rather than tied to a lead-specific tool implementation. Management contributes protected design/member parts, lead model discovery and file validation. Implementation contributes the derived code part and an independently committed context part for each working node. Execute contributes existing general command allowances and reusable web_search/web_fetch independently of Bash permission. The [web tools](../../web-tools/design.md) own backend-only DeepSeek requests, input validation and deterministic Markdown-plus-metadata output; no web provider logic is added to the runtime loop. Management gives non-lead members only ls/read and no writable design scope. Base rule text lives under backend/prompts/harness as Markdown, including management/design/member, implementation/code-scope/context-scope, bootstrap design/context templates, execute and shared prompts. harness-prompts loads required files once relative to its module URL and renders backend-owned template values. Runtime and inspection share the same renderer. Member Markdown remains separate; enforcement stays in the base definitions, file boundary and Git/Bash services. Missing/empty files fail startup; unresolved template variables fail assembly. There are no embedded fallback rules. Build copies the required assets to dist/prompts/harness so compiled modules load their own release files independently of cwd. Prompt edits take effect after restart (and rebuild for compiled use).

Design/implementation rules and bootstrap Markdown templates explicitly distinguish document organization from subsystem boundaries. Interface and Implemented contracts share the node's caller perspective; the latter gives actual precise usage, with internal notes as supporting context. The structural parser does not infer boundaries from Markdown topics or enforce semantic prose completeness.

## Coordination and data flow

1. Resolve accepted working/dependency designs and derive writable/read-only paths. Validate/control exclusions and dependency precedence define file access. Materialize missing active member bundles for the lead without replacing drafts.
2. Open private bare storage inside the managed root at .rsi/harness/repository.git and one linked worktree per member. Initialize scope refs by normalized paths/exclusions and optional context selector, preserving existing pending work when the shape changes.
3. Assemble unique ls/read/write/edit/bash/web_search/web_fetch plus lead list_models and validate_member_config. File tools resolve through MemberFiles. Bash resolves requested scope against current parts; supplied metadata can select only that scope.
4. For scoped Git, create one backend-only bare metadata directory under staging/<member>/<part>/<scope-hash>. It has its own HEAD/index and shares the main object directory through GIT_OBJECT_DIRECTORY. Private repositories, worktree .git and backend storage are unreadable/unwritable to shell children.
5. A per-invocation Unix socket receives actual Git argv/cwd from the immutable PATH Git bridge. Backend validates cwd, command/options/path intersection, source revisions and actor policy. Native Git runs with explicit private git-dir/worktree, no global/system config, hooks, fsmonitor or external diff/textconv. Protected acceptance is serialized across design parts as well as per-scope implementation acceptance. Stage integrity is checked; failed add restores the index. Commit performs compare-and-swap accepted/base updates under a scope queue. Protected commits refuse before acceptance.
6. @anthropic-ai/sandbox-runtime 0.0.79 wraps real Bash in sandbox-exec on macOS or bubblewrap on Linux. Read scope includes authorized node metadata, design/implementation/context and required runtime/system files. General writes permit implementation minus control/dependency paths; Git Bash permits scratch only. Metadata selection never authorizes unrestricted execution. Profiles are generated under a queue because the SDK reads global Unix-socket configuration; running commands remain parallel across members. No unsandboxed fallback/network allowance is provided.
7. Minimal child environment omits backend credentials/config. Processes run in a detached group with bounded output/timeout. End/abort kills descendants; broker operations settle before temp cleanup and lifecycle checkpointing. The bridge uses exported PWD for cwd (validated by backend), avoiding directory-content access required by Node getcwd in an otherwise unassigned root.
8. Checkpoints build trees through fresh temporary indexes and update checkpoint/run refs, never the agent index. User acceptance validates exact working snapshot/review/base and updates accepted/base refs atomically. Git staging synchronizes HEAD after user acceptance, refreshing a clean index but retaining dirty staging. Explicit full index/worktree restore to current acceptance refreshes stale bases. Git log --all resolves to the selected checkpoint and acceptance heads, never arbitrary repository refs; working restores checkpoint pending files before replacement.
9. A user design commit atomically updates per-design accepted pointers alongside scope refs. DesignService reads those accepted bytes first, with tombstones for deleted records, then original context for paths never accepted in harness Git. Pending bytes and member-file commits cannot grant design authority.

## Decisions and constraints

The actual Git bridge is the trusted operation boundary; OS isolation prevents native Git/repository access and arbitrary shell writes from bypassing it. Scope selection is one per Bash invocation. Supported Git syntax is intentionally finite and documented; arbitrary native Git flags, remote operations and shell repository selection are not forwarded.

General execution still uses exact-vector/executable rules over [bash,-c,command]. Only a Bash allowance authorizes general scripts. Richer rules are deferred. Linux requires sandbox runtime dependencies and allows Unix socket transport; this task verifies the macOS profile. Temporary scratch/system runtime access is execution infrastructure, not workspace ownership.

Accepted design pointers supply semantic reads without mutating original-context history or auto-refreshing peer worktrees. User member acceptance and user member activation remain separate actions. Startup removes legacy explicit paths from assignment records and migrates accepted sources, preserving exact previous bundles and pending work; archived scope refs and retired records remain historical.

## Member configuration file review support

HarnessHistory supplies bounded immutable file previews, trusted import of database source text into a temporary Git tree, per-file unified patches and committed-chain history since an activation boundary. These operations share private objects and do not modify a member's working files or staged index. Team owns source interpretation, activation baseline persistence and endpoint responses.


## Managed-root storage and staging

The private repository/worktrees live under .rsi/harness in the registered project. Snapshot traversal always excludes this private subtree, including when seeding a whole project, so it cannot recursively snapshot itself. Seed discovery includes managed context/member files despite project ignore rules. File tools hide all private .rsi subtrees and Git metadata; Bash protects .rsi and allows only authorized narrower management reads. Implementation-code scope excludes the complete .rsi root. The separate implementation-context parts grant only their selected node’s impl.md/impl/ paths. Scoped Git add enumerates authorized regular files and tracked deletions, then passes literal NUL-delimited pathspecs through native Git stdin; it uses the same flow for directory and individual-file scopes and preserves unrelated staging.

## Unified system-context composition

workspace-layout derives metadata references, design.md/design and impl.md/impl paths and classifies ownership by the first content boundary. Context directories contain documents for one system, not child node identities. resolveHarness resolves metadata/Markdown from accepted design state; safe raw assignment parsing stays separate from semantic resolution. Invalid references remain inspectable/unready. Inspection omits invalid derived context parts rather than granting authority. Runtime preparation resolves actual node spelling before assembling parts.

harnessAccess grants only the selected node's context, with read-only dependency precedence and listable ancestor folders. The lead can create/manage design metadata/documents anywhere while unrelated impl context stays hidden. MemberFiles checks actual file mutation; mkdir of an already existing visible directory is a no-op, so common write tools can reach a dependency parent without acquiring write permission. Creating a directory still checks authority. Managed .rsi control roots keep canonical spelling, context writes use shared path/depth limits and links/private state remain refused.

HarnessPart.context is an enforced design or impl selector. partOwns, snapshot traversal and index validation apply it before collecting files. validateParts recognizes the two disjoint context domains. Scope keys normalize case and include selector plus both representation paths, so impl.md to impl/ transitions reuse history. Context Git status enumerates only owned current/tracked files; staging enumerates owned literal paths, preventing new-node impl files from appearing in design history. Scoped restores/removes operate the selected tracked snapshot and cannot cross selectors.

User design acceptance reads immutable checkpoint bytes, decodes UTF-8 and resolveDesign-validates every contained node before advancing accepted refs. Native agent implementation-context commits validate the actual staged tree through contextDocuments; generic user scope acceptance validates its selected context tree as well. Simultaneous forms, non-Markdown entries, absent README and document limits refuse semantic acceptance without losing index or pending bytes. Checkpoints do not enforce semantic readiness and retain incomplete intermediate work.

Bash read scopes contain exact selected design/context paths. Lead-only design search enumerates its current metadata/design files instead of granting broad .rsi/context reads that would expose others' impl context; excessive listing fails closed. All .rsi remains protected from general shell writes. No new history algorithm, model loop or tool is introduced. Existing peers/raw ContextBase are not refreshed from scope commits.

[Context-tree tests](../../../../backend/test/context-tree.test.ts) cover document representations, node identity, exact-node/dependency permissions, new-node design isolation, immutable acceptance, independent transitions, inherited committed context, case spelling and unavailable-reference inspection. Existing sandbox/native Git, member lifecycle, runtime finalization and SQL tests remain applicable.

HarnessPermissions resolves working and dependencies, each with designContext, implementationContext and implementation arrays. harnessAccess and Bash read-scope assembly consume that model. Lead working designContext is the whole design root; its implementation arrays stay assignment-derived. Other members have no design part, receive read-only node views and cannot select design Git. designBaseline overlays accepted per-file design additions/deletions when a new view is opened. Read-only views include their accepted design revision in backend-owned scope identity, so an earlier shared baseline cannot hide a newer accepted design. Existing implementation history/peer worktrees are not refreshed. Prompt assembly includes the resolved permission components.

Read-only design views follow the currently resolved accepted node revision on the next environment assembly. They can replace earlier read-only design representations, including removing accepted tombstones. Implementation context/code and pending lead management work are not overwritten by that read-only member-view projection.

## Web-tool assembly

main.ts constructs webTools(process.env.DEEPSEEK_WEB_API_KEY) once and passes the reusable implementations through TeamSystem to HarnessService. prepare filters them through the fixed execute base alongside the existing catalog; runtime and inspection use the same base capability definitions. An in-process caller can inject implementations for testing/reuse; defaults retain the capability definitions but explicitly fail execution without credentials. No key enters harness definitions, member configuration, system prompts or database config. execute.md supplies usage/filter/attribution and external-content rules.

The [web tools implementation](../../web-tools/impl.md) owns the fixed HTTP endpoints, cancellation/deadline/body limits, safe provider errors and rendering. The existing runtime persists each complete text tool result and exposes it through database-backed follow; no frontend storage or runtime-loop changes are required. Web HTTP does not relax sandbox network or file authority.
